G1-D 自主导航系统原理

工程 g1d_ros2_ws（ROS 2 Jazzy）· 本文讲"为什么这样设计、每一块怎么工作"。上机步骤见 docs/BRINGUP_GUIDE.md，参数清单见 docs/DEPLOYMENT.md，标定见 docs/CALIBRATION.md。

1. 目标与总体思路

宇树 G1-D 是"人形上身 + 差速轮式底盘"的机器人。它的底盘有两个先天限制：

  • 运动控制只有一个 DDS 话题 rt/cmd_vel_no_limit：没有限幅、没有避障，谁写进去底盘就照做；
  • 底盘的单线雷达只扫一个高度平面，看不到桌沿、货架隔板等悬空障碍——机器人上身会撞上去。

工程用头部倒装的 Livox Mid-360S（360° × 59° 视场的多线激光雷达，内置 IMU）解决感知问题，在 ROS 2 上实现建图、定位、导航避障，并用一个独立的"守护"节点兜住安全：

功能做法主要组件
里程计激光 + IMU 紧耦合，10 Hz 位姿 + 去畸变点云；轮速计在两帧之间外推到 50 HzFAST_LIO、lio_bridge
建图关键帧位姿图 + 闭环检测，保存三维点云地图和"高度带"二维栅格pgo（GTSAM）、map_manager
定位在先验点云地图上持续配准，发布 map → odom；自动全局初始化small_gicp、localization_monitor
导航全局规划 + 局部控制；代价地图用三维体素保留悬空障碍Nav2（NavFn + RPP）、nav_manager
安全/cmd_vel_no_limit 唯一写入者：限幅、加减速、看门狗、扫掠路径反射停车、急停、遥控接管g1d_guard
大模型接入NavGPT 给出"图像时刻的相对航点"，按 TF 历史补偿推理延迟NavigateRelative action
贯穿全局的三条设计原则
① 不改动宇树系统：PC2 上不装任何东西，所有节点跑在外接的导航主机上；
② 安全不依赖导航栈：导航栈任何部分崩溃、卡死，守护都能在 0.6 s 内让底盘停下；
③ 算法与 ROS 解耦：核心算法放在纯 Python 包 g1d_core，可在 Windows 上单元测试；ROS 节点只做收发。

2. 部署架构与通信

2.1 为什么不需要桥接

宇树 SDK2 底层就是 CycloneDDS，话题名和类型遵循 ROS 2 的映射规则：DDS 话题 rt/lowstate 就是 ROS 2 的 /lowstate，DDS 类型 unitree_hg::msg::dds_::LowState_ 就是 ROS 2 的 unitree_hg/msg/LowState。只要两边 CycloneDDS 版本兼容（SDK2 为 0.10.2，Jazzy 的 rmw_cyclonedds_cpp 也是 0.10.x）、域号相同（0），ROS 2 节点就能直接订阅、发布宇树话题。工程只编译 unitree_ros2 里的消息包，不需要任何桥接进程。

g1d_env.sh 设置 RMW_IMPLEMENTATION=rmw_cyclonedds_cpp、ROS_DOMAIN_ID=0 和 CYCLONEDDS_URI：网线连接时在指定网卡上用组播发现；WiFi 时改为单播发现 PC2（组播在多数路由器上不可靠）。

2.2 QoS

宇树话题和传感器话题都是 best-effort（可靠性"尽力而为"）。ROS 2 中可靠订阅者收不到 best-effort 发布者的数据，所以所有订阅宇树 / 传感器话题的节点都用 best-effort（ros2 topic echo 要加 --qos-reliability best_effort）。守护写 /cmd_vel_no_limit 用 reliable，底盘侧任意 QoS 都能收到。

3. 坐标系与时间

3.1 关键坐标系

坐标系含义
base_link底盘中心在地面上的投影（z = 地面），x 向前。导航、守护、代价地图都以它为准
odomLIO 启动时 base_link 的位置。连续、平滑，但长时间会漂移
map先验地图坐标系 = 建图那次会话的 odom。map → odom 由重定位修正漂移
livox_frame / livox_imu雷达点云坐标系 / 内置 IMU 坐标系。FAST_LIO 的"机体系"就是 livox_imu
lio_worldFAST_LIO 自己的世界系（启动时 IMU 的位姿），不挂在 TF 树上，由 lio_bridge 换算到 odom

头部雷达不是固定在底盘上的：它随升降、腰俯仰、腰偏航运动。body_state 把宇树关节反馈转成 /joint_states，robot_state_publisher 按 URDF 正运动学实时给出 base_link → livox_imu。因此即使升降高度变了，LIO 换算出的 base_link 位姿仍然正确（单元测试 test_lift_change_keeps_base_pose）。

3.2 时间戳策略：一切以导航主机时钟为准

多台计算机、多个数据源的时间戳如果不一致，TF 查询会失败或取到错误的历史位姿。工程不要求 PC2 与主机做时钟同步，而是逐个数据源处理：

数据源原始时间戳处理
SLAMWARE odom / scan比主机慢约 181 s，且每天漂移数秒chassis_restamp 按接收时刻重打（可减去固定延迟 odom_latency），并定期打印原始偏差
宇树关节话题没有消息头按接收时刻
Mid-360S雷达未做 PTP 同步时，驱动用主机 high_resolution_clock 给每个包打戳本来就是主机时钟（读源码确认，无需补丁）
map → odom上游用"最近一帧扫描时间 + 0.1 s"改为当前时钟 + 0.1 s（扫描带着约 0.5 s 的 LIO 延迟，Nav2 会报变换过旧）
定位状态位姿—用该位姿对应的 TF 时间戳，而不是发布时刻（否则行驶中会多算一段距离）

4. 身体状态与姿态锁定

body_state 订阅三路宇树话题并发布 /joint_states（50 Hz）：

  • /hispeed_state（Point32：y = 升降高度，z = 升降速度）→ URDF 两段升降关节，各取 (lift_scale·y + lift_offset)/2；
  • /waistpitchstate（MotorState.q）→ 腰俯仰（URDF 里名为 Yaw_Joint，实际是俯仰）；
  • /lowstate（unitree_hg LowState）：序号 12 = 腰偏航（torso_Joint），15–28 = 双臂 14 个关节。

姿态锁定：导航期间头部雷达相对底盘必须不动，否则代价地图里的点会"拖影"、守护的自身点过滤会失效。/g1d/body_lock 报告当前姿态与"导航姿态"（nav_waist_pitch、arm_tuck，腰偏航为 0）的偏差：腰 2°、手臂 5°、升降 1 cm、升降速度 5 mm/s，任一超限或数据超时 0.5 s 即"未锁定"，nav_manager 拒绝 / 中止导航（body_not_locked / body_moved）。

5. 激光惯性里程计（LIO）

5.1 自身点过滤

头部雷达倒装、向下看，会扫到自己的躯干、手臂和底盘。self_filter（C++）在 FAST_LIO 之前删除落在若干"身体盒子"里的点：盒子定义在各自的连杆坐标系里（躯干、手臂在 head_link，底盘在 base_link），每帧按 TF 放置，所以身体动了盒子也跟着动。另外删除 0.3 m 以内的点。漏网的自身点会让代价地图在机器人身边出现"幽灵障碍"、守护误停车。

5.2 FAST_LIO 的原理

FAST_LIO 是紧耦合的激光惯性里程计，核心是迭代误差状态卡尔曼滤波（IESKF）：

  1. IMU 前向传播：用 200 Hz 的 IMU 积分预测这一帧扫描期间的位姿、速度，状态还包括 IMU 零偏和重力；
  2. 反向传播去畸变：Mid-360 一帧（0.1 s）内的点是在不同时刻测的，机器人在动。按每个点的时间戳把它变换到帧末时刻，消除运动畸变；
  3. 点到平面残差：降采样（0.3 m）后的每个点，在地图（ikd-Tree 增量 kd 树，0.4 m 体素）里找 5 个最近邻拟合平面，残差是点到平面的距离；
  4. 迭代更新：以残差为观测迭代更新状态（最多 3 次），得到帧末位姿；
  5. 地图增量更新：把这一帧的点按位姿加入 ikd-Tree。

输出：/Odometry（lio_world → livox_imu，10 Hz）和去畸变的当帧点云 /cloud_registered_body（livox_imu 系），后者被重映射为 /g1d/obstacle_cloud，同时供代价地图、守护和建图使用。blind 0.6 进一步剔除 0.6 m 内的点（自身遮挡）。

5.3 lio_bridge：从 IMU 位姿到底盘位姿

FAST_LIO 估计的是 IMU 在 lio_world 中的位姿 Tlio,imu(t)。odom 锚定在第一帧：令启动时的底盘位于 odom 原点（z = 地面）：

Todom,lio = Tbase,imu(q0) · Tlio,imu(t0)−1
Todom,base(t) = Todom,lio · Tlio,imu(t) · Tbase,imu(qt)−1

其中 qt 是 t 时刻的关节角（由 TF 查询 base_link → livox_imu）。发布的位姿是平面的（x, y, yaw）；z、横滚、俯仰只用于健康检查。T_odom,lio 以 latched 话题 /g1d/lio_anchor 发布，建图模块用它把 pgo 的地图换算到 odom 系。

轮速外推：LIO 只有 10 Hz 且有处理延迟，而控制器和守护需要"现在"的位姿。lio_bridge 以 50 Hz 发布 TF odom → base_link：

pose(now) = poseLIO(tk) ⊕ Δwheel(tk → now)，　仅当 now − tk ≤ 0.5 s

Δwheel 是 SLAMWARE 轮速里程计在这段时间内的增量（在底盘坐标系中）。超过 0.5 s 没有 LIO 就停止发布，下游会因 TF 超时停车。

5.4 健康监测

检查阈值典型原因
LIO 超时0.5 s 无更新雷达断线、FAST_LIO 卡死
跳变相邻两帧 > 0.3 m 或 > 15°退化场景匹配错误
z 漂移 / 倾斜|z| > 0.3 m，横滚 / 俯仰 > 10°外参错误、重力估计错误
与轮速不一致2 s 窗口内位移差 > 0.3 m 或航向差 > 10°长走廊退化、轮子打滑

每个错误至少保持 1 s，避免抖动。结果发布在 /g1d/lio_health，nav_manager 据此中止导航（lio_lost）。

5.5 FAST_LIO 崩溃恢复

FAST_LIO 的 ROS 2 版本在负载高时偶发启动段错误（上游 issue #51，原因未明）。工程的对策：launch 设置 respawn 自动重启；重启后的 FAST_LIO 有一个新的 lio_world，lio_bridge 检测到两次 LIO 更新间隔 > 1 s 时重新锚定：

expected = poselast ⊕ Δwheel(tlast → t)，　Todom,lio ← T(expected) · Tbase,imu · Tlio,imu(t)−1

即用"上次位姿 + 断档期间的轮速运动"续接，odom 保持连续（中断期间守护因点云超时已经停车）。建图时不自动重启（重启会破坏位姿图），需重新建图。

6. 建图

6.1 位姿图与闭环

LIO 有累积漂移，绕一大圈回到起点时位置会对不上。pgo（来自 FASTLIO2_ROS2）在 LIO 之上做关键帧位姿图优化：

  1. 每移动 0.5 m 或转 10° 取一个关键帧（位姿 + 当帧点云）；
  2. 闭环检测：当前关键帧与 1 m 以内、30 s 以前的历史关键帧组成候选，用 ICP 把当前帧与历史子图（前后各 5 帧）配准，fitness < 0.15 才接受；
  3. 相邻关键帧之间加里程计约束，闭环加闭环约束，用 GTSAM iSAM2 增量优化，修正整条轨迹。

6.2 地图导出

/g1d/save_map 时，map_manager 取优化后的关键帧，用 /g1d/lio_anchor 把它们换算到 odom 系（这次会话的 odom 即将来的 map 系），输出：

文件内容用途
map.pcd拼接后的点云，5 cm 体素降采样重定位配准的目标
map.yaml / map.pgm"高度带"二维栅格，5 cmNav2 静态层、Web 显示
trajectory.csv关键帧轨迹自动重定位的搜索种子
keyframes/、meta.yaml各关键帧点云与位姿、建图信息离线分析、重建

6.3 高度带栅格：让二维地图表示悬空障碍

普通二维栅格只看一个高度平面。本工程把高度带 0.08 – 1.85 m 内所有点投影到地面：一个格子里有 ≥ 2 个点落在这个高度带内就标为占据——桌面（0.75 m）、货架隔板、横杆都会成为占据格；地面附近（−0.10 – 0.05 m）有点且没有占据的格子标为空闲，并向未知区域扩一格；其余为未知。0.08 m 的下限滤掉地面起伏和地毯，1.85 m 的上限让门框、吊灯等高处物体不挡路（上限应高于机器人最高点，上机时按实测身高核对）。

7. 先验地图定位

7.1 持续重定位（small_gicp）

odom 会漂移，map → odom 负责把它拉回地图。lio_bridge 把每帧去畸变点云变换到 odom 系发布为 /g1d/registered_scan（≤ 20000 点）。small_gicp_relocalization 每 0.5 s 取最近 5 帧，0.2 m 体素降采样后用 GICP（广义 ICP：每个点带局部协方差，按"分布到分布"计算误差，比点到点 ICP 收敛更稳）与 map.pcd 配准，初值为上一次的结果，对应距离上限 1 m、最多 10 次迭代。结果就是 Tmap,odom，以 20 Hz 发布。

工程对上游做了三处修改：时钟打戳（见 3.2）；配准放到独立线程（单线程时一次配准期间 map → odom 停发，Nav2 报变换过旧）；只配准最近 N 帧（多线程后若无上限累积，配准越来越慢）。

7.2 自动初始化（全局搜索）

GICP 只能在初值附近收敛。上电时机器人在地图的哪里？g1d_core.reloc 做一次全局搜索：

  1. 候选：建图轨迹每 0.5 m 取一个种子，每个种子周围 ±0.25 m 的 3×3 偏移，航向每 10° 一个；
  2. 评分：把最近 1.5 s 的扫描（≤ 1500 点）按候选位姿变换到地图，得分 = 落在地图占据体素中的点的比例；
  3. 细化：取前 5 名做由粗到细的爬山搜索；
  4. 判定：最高分 < 0.6 视为没找到；最高分与"明显不同的次优解"接近时报告歧义（对称场景）。

找到的位姿作为 /initialpose 交给 small_gicp 精配准。初始位姿也可以来自 RViz 的 2D Pose Estimate、Web，或上次关机前保存的位姿（last_pose.yaml）。

7.3 定位健康判据

判定"丢失"的标准经过实测修正——最初的"3 s 没有成功配准即丢失"在主机负载高时会误报（当时内点率其实是 0.995，只是配准变慢）。现在的判据：

情况判定原因码
收敛且内点率 ≥ 0.5正常—
连续 4 次配准失败（不收敛或内点率低）丢失registration_failing
3–10 s 没有新结果仍定位，只提示registration_slow
10 s 没有新结果丢失registration_stale

理由：LIO 健康时，map → odom 几秒不更新只带来厘米级漂移（0.35 m/s 行驶 10 s 约 3.5 cm）。

7.4 纯里程计模式

没有先验地图时（mode:=odom），map → odom 为静态单位变换，全局代价地图改为 20 m × 20 m 滚动窗口，导航目标用 odom / base 坐标。

8. 代价地图与悬空障碍

Nav2 代价地图是多层叠加的栅格：

层数据参数
静态层（仅 map 模式全局图）map.pgm来自建图
体素层/g1d/obstacle_cloud（Mid-360S）高度 0.08 – 1.88 m，15 层 × 0.12 m，标记 5 m，射线清除 6 m
障碍层/chassis/scan（底盘雷达）标记 4 m，清除 5 m
膨胀层—半径 0.55 m，衰减系数 3.0；底盘轮廓 0.60 × 0.56 m

8.1 为什么要用三维体素层

代价地图除了"标记"障碍，还要"清除"已经不在的障碍：从传感器原点向每个测量点画一条射线，射线穿过的格子清空。二维障碍层的射线清除是整列的——一条射向桌子后方地面的射线，在二维投影上穿过桌面所在的格子，桌面就被清掉了，机器人以为可以通过，上身撞上桌沿。

体素层把空间分成 15 层，射线只清除它真正穿过的高度的体素。从头部射向桌子后方地面的射线，凡是能落到地面的，经过桌子上方时都高于桌面（否则就打在桌面上了），所以它只清除桌面以上的体素，桌面体素保留，投影到二维后桌子仍是障碍。这是 CI 集成测试 T6"桌面悬空"验证的关键点。

9. 规划与控制

9.1 全局规划

NavFn（Dijkstra 势场）在全局代价地图上规划路径，允许穿过未知区域（纯里程计模式下未探索区域都是未知），目标容差 0.3 m。行为树每秒重新规划一次，环境变化后路径会更新。

9.2 局部控制：Regulated Pure Pursuit（默认）

纯追踪的思想：在路径上取机器人前方距离 L 处的"胡萝卜点"，求一段经过当前位姿与该点的圆弧。设胡萝卜点在机器人坐标系中的横向偏移为 yc：

曲率 κ = 2 · yc / L2，　角速度 ω = v · κ

"Regulated"指线速度按情况降低：转弯半径小于 0.9 m 时按曲率降速（下限 0.1 m/s）；前瞻 1.0 s 的轨迹若与代价地图碰撞则停止。其他参数：期望速度 0.35 m/s（小于守护上限 0.40）、前视距离固定 0.6 m；与路径夹角大于 45° 时先以 0.5 rad/s 原地转向（差速底盘起步时避免大弧线），到达后对齐终点朝向。

9.3 MPPI（可选，controller:=mppi）

MPPI（模型预测路径积分）每个周期随机采样数百条控制序列，用运动学模型展开成轨迹，按一组"代价函数"（离障碍物距离、跟随路径、朝向目标、偏好前进等）评分，再按 softmax 加权平均得到最优控制。它对动态障碍更灵活，但参数多。工程沿用的 MPPI 参数在 CI 仿真中只有约 0.05 m/s 且不跟随路径，用并行对照实验定位到 regenerate_noises: false：整个运行期复用同一组随机噪声样本，小批量下样本均值的偏差变成了系统性偏转。改为 true 后用例全部通过，但 RPP 更快更稳，所以默认使用 RPP。

9.4 失败与恢复

进展检查：8 s 内移动不到 0.2 m 视为卡住，行为树依次尝试清除代价地图、原地转、等待、后退；恢复用尽则导航失败，nav_manager 把 Nav2 错误码映射为 no_path、blocked、timeout 等原因。

10. 导航管理与 NavGPT 接入

nav_manager 提供 /g1d/navigate_relative action（g1d_msgs/action/NavigateRelative），是 NavGPT、Web、命令行工具共用的入口。

10.1 模式与坐标系

mode行为
navigate目标处理后交给 Nav2（规划 + 控制）
rotate原地转到指定朝向（Nav2 Spin）
simple先转向目标方位，再直行指定距离（不规划，守护仍然生效）
stop取消当前目标

frame 可以是 base_at_stamp（默认）、base、odom、map。

10.2 推理延迟补偿

NavGPT 看到的是图像拍摄时刻的画面，给出的"前方 1 m"是相对那个时刻的机器人；而推理要几秒，期间机器人可能已经转了身。base_at_stamp 用 TF 历史（缓存 15 s）查询图像时刻的底盘位姿：

goalglobal = Tglobal,base(stamp) · (x, y, yaw)

stamp 早于 5 s 或晚于当前 1 s 拒绝（goal_stamp_unavailable）。CI 测试：记下时间戳后原地转 90°，再发"旧时刻前方 1 m"的目标，机器人仍到达旧朝向前方 1 m 处。

10.3 目标处理

  1. 截断：超过 9 m 的目标截断到 9 m（partial）；
  2. 可行性：在全局代价地图上查目标格子，代价 ≥ 50（OccupancyGrid 0–100）视为不可停；
  3. 外移：先沿"目标 → 机器人"方向回退（最多 1.0 m 加两格量化余量）；不行再在 1.0 m 内找使 d目标 + 0.3·d机器人 最小的可行格——离目标近、并且偏向机器人一侧，避免绕到障碍背面（adjusted）；
  4. 找不到可行点 → goal_in_obstacle；目标在地图外 → goal_out_of_range。

10.4 运行中的中止条件与失败反馈

执行期间每 0.1 s 检查：姿态锁定、LIO 健康、定位状态、守护急停 / 人工接管、超时。失败结果除原因码外还带 free_sectors：在局部代价地图上检查机器人朝向 −90°、−60° … +90° 七个方向 1.5 m 的通道是否畅通。prompt_feedback() 把这些转成一行文字附加到下一轮 NavGPT 提示词，例如 [导航失败] 原因=blocked 可通行方向(度)=30,60；到达的是截断后的目标时提示"请继续给出下一个航点"。

旧版 JSON 接口（/nav/goal、/nav/status，与非 ROS 版本 g1d_ws 相同）由兼容层转成 action。

11. 安全设计（守护 g1d_guard）

11.1 五层防护

层机制失效时由谁兜底
L1代价地图 + 控制器（RPP 碰撞前瞻）L2
L2守护反射层：整车矩形沿指令圆弧扫掠，0.45 m 停车 / 1.2 m 减速、后退保护、原地旋转圆 0.38 mL3
L3守护看门狗：导航指令 0.25 s、传感器 0.5 s 超时即停L4
L4急停锁存：/g1d/estop、底盘碰撞 / 悬崖事件、Web 急停L5
L5底盘自身指令超时、AEB、硬件急停按钮—

11.2 每个控制周期（30 Hz）做什么

  • 指令源：急停锁存或遥控器接管时目标速度为零；否则 Web 遥控（0.3 s 内有新指令，限速 0.30 m/s）优先于导航指令（0.25 s 内有新指令）；都没有则为零。
  • 传感器新鲜度：底盘雷达 0.5 s 内必须有数据；require_cloud 时 Mid-360S 点云也必须新鲜（P1 阶段只用底盘雷达时可关闭）。
  • 零速保持：速度归零后继续发零速 zero_hold（默认 1 s）再停止发布，把底盘"让"给遥控器或其他程序；遥控器接管期间完全不写。

11.3 扫掠路径检测

传统做法是看前方一个扇区里有没有点，转弯时要么误停、要么漏检。守护把整个底盘矩形（前沿 0.28 m、后沿 0.30 m、半宽 0.30 m）沿当前指令 (v, ω) 的圆弧向前"扫"，曲率 k = ω / |v|，步长 min(0.05 m, 0.05 rad / |k|)，最多扫四分之一圈或 1.2 m，求第一个碰到障碍点时走过的弧长 d：

v′ = max( v · (d − 0.45) / (1.2 − 0.45),　min(v, 0.05) )

0.05 m/s 的"爬行下限"保证机器人真正开到停车线，而不是无限逼近。后退时同样扫掠，后方 0.5 m 内有障碍禁止后退；原地旋转（|v| < 0.05）时 0.38 m 圆内有点禁止旋转。底盘轮廓内的点（|x| < 0.30、|y| < 0.28）视为自身回波忽略。

11.4 停车时间与"不能刹太猛"

导航栈卡死时，守护在最后一条指令后 cmd_timeout 开始减速：

tstop = cmd_timeout + vmax / abrake = 0.25 + 0.40 / 1.5 ≈ 0.52 s　≤ 0.6 s

CI 实测：指令 0.49 s 归零、仿真底盘 0.50–0.52 s 停住。为什么不加大减速度缩短停车时间？G1-D 重心高（约 1 m）、底盘短（半长约 0.28 m），急刹会前倾。准静态近似下，前倾临界减速度：

acrit ≈ g · d / h = 9.81 × 0.28 / 1.0 ≈ 2.7 m/s²

1.5 m/s² 留有约 45% 余量。因此改为降低最高速度（vx_max 0.40）来满足停车时间要求。急停和遥控接管不走减速斜坡，直接输出零（底盘自身决定如何停）。

11.5 其他安全机制

  • 唯一写入者：守护启动前等待 1.5 s 的 DDS 发现，若 /cmd_vel_no_limit 已有其他发布者（包括非 ROS 的 DDS 写入者）就拒绝启动；启动时还会通过底盘 HTTP 取消 SLAMWARE 自身正在执行的动作。
  • 急停锁存：/g1d/estop 为 true、底盘碰撞（BUMPER_TRIGGERED）或悬崖（CLIFF_DETECTED）事件都会锁存急停，只认守护启动之后的新事件；只能人工解除（确认现场安全后发 false）。
  • 遥控器接管：/wirelesscontroller 任一摇杆超过死区 0.15，守护在 5 s 内不写底盘，导航中止（manual_override）。
  • 主机 / 网络故障：守护本身挂了只能靠底盘自身超时（L5），所以上机第 0 阶段用 cmd_vel_probe 实测"停发后底盘多久停"，≤ 0.6 s 才放行自主导航。

15. 已知限制

  • 导航期间身体必须保持导航姿态，未做运动中的身体补偿；
  • 动态行人只靠体素射线清除和守护反射层处理，没有运动预测；
  • 长走廊、空旷大厅等几何退化场景 LIO 可能失效（健康监测会报告并停止导航）；
  • 自动重定位要求机器人在建图轨迹附近；完全陌生的位置需手动给初值；
  • 单层平面场景，未覆盖楼梯、坡道、多楼层；
  • 玻璃、镜面等激光难以测量的障碍需要底盘 AEB 或人工规避。
